深入分析进程虚拟地址空间的划分——用户空间与内核空间、.text/.rodata/.data/.bss/堆/共享库/栈区

一段C++的代码

一个问题：这段代码经过编译链接产生可执行文件，运行时，这些变量分别放在内存的哪里？

进程的虚拟地址空间

任何编程语言写出的代码，无非产生两样东西：指令和数据。

程序编译链接完成后，在 Windows 上是一个 .exe 可执行文件，放在磁盘上。CPU 无法直接运行磁盘上的程序，需要先把它从磁盘加载到内存。这就产生了问题：加载到内存的哪里？内存有没有区域划分？划分后是什么样？

这里以x86 体系、32 位 Linux 环境为例进行说明：

程序运行时，Linux 内核会给当前进程分配一块大小为 2^32 的空间，也就是 4G。这块空间叫做进程的虚拟地址空间。

虚拟地址空间并不是物理内存上的一块真实空间。从底层原理上说，它只是内核创建的一系列数据结构而已。

⚠️ 虚拟内存 ≠ 虚拟地址空间，这是两个不同的词，不要混用。

另外，4G 是跟系统位数绑定的：如果是 64 位 Linux，每个进程的虚拟地址空间是 2^64。但是原理是一样的。

空间的划分：用户空间 + 内核空间

这 4G 空间默认被划分成两部分：

区域 范围 大小
用户空间 user space 0x00000000 ~ 0xC0000000 3G
内核空间 kernel space 0xC0000000 ~ 0xFFFFFFFF 1G

32 位 Linux 下，系统默认内核空间占 1G、用户空间占 3G。这个比例可以通过修改操作系统配置来调整，但默认就是这样。

每一个进程都有这么一个虚拟地址空间。

用户空间的布局，从低地址到高地址

用户空间并不是从 0 地址就开始存放内容的，前面空了一段。

函数里定义这样一个局部变量指针，指针 p 本身在栈上，但它指向的常量字符串 "hello world" 存储在 .rodata 段。

那能不能通过指针修改这个字符串的第一个字符？

编译能通过，但运行会崩溃——因为 .rodata 段跟 .text 段都只能读、不能写。

较新的 C++ 编译器已经不允许用普通指针指向常量字符串，写的时候必须加 const 修饰。指向被 const 约束后，这类不可预期的错误也就不会发生了。

段 存放内容

对应到开头那段代码：

  • gdata1 = 10、gdata4 = 11 → 初始化且不为零 → .data
  • gdata2 = 0、gdata3、gdata5 = 0、gdata6 → 为零或未初始化 → .bss
  • e = 13 → 静态局部变量，初始化且不为零 → .data
  • f = 0、g → 静态局部变量，为零或未初始化 → .bss

为什么未初始化的全局变量打印出来是 0？

因为它存放在 .bss 段。程序运行时，操作系统内核给当前进程分配地址空间，把未初始化的数据放在 .bss。然后内核会自己负责把 .bss 段的数据全部清零——所以我们看到未初始化的全局变量打印出来是 0，这是操作系统对 .bss 段默认做的零初始化。

而局部变量 c 没初始化，打印出来肯定不为 0，因为它是栈上的无效值，跟 .bss 的零初始化不是一回事。

栈有两点特别重要：

  1. 每个线程在当前进程私有的也只有栈
  2. 栈是从高地址往低地址增长（和堆的从低到高刚好相反）

用户空间私有，内核空间共享

值得注意的是：

每一个进程的用户空间是私有的，但内核空间是共享的。

画三个进程来理解：

  • 每个进程（比如QQ、酷狗音乐、VS Code）各自都有各自的用户空间，用户空间是私有的
  • 但内核空间是共享的，所有进程共用同一块

这也解释了操作系统里的进程间通信问题。进程之间通信比较难的原因，就是用户空间是隔离的——谁也访问不到谁，就像你在一个房间、我在另一个房间，根本没法说话。

而匿名管道通信的原理就清楚了：在内核空间划分一块内存，进程一往这块共享内存里写数据，进程二、进程三都能看得见；进程二或进程三往里写，其他进程也都能看得见。

回到代码

把开头那段代码加上注释再看一遍，现在应该都能看懂了：

符号表是什么

编译一个源文件时，编译器会把当前文件里定义的、能被别的文件”看见”的名字记下来，列成一张表，这张表就叫符号表。每个条目大致记三件事：

记录内容 例子
名字 gdata1
类型和大小 int，4 字节
所在位置 哪个段、什么偏移

它是干什么用的？ 主要服务于链接。

一个程序往往拆成多个 .cpp，每个单独编译成 .o（目标文件）。链接器要把它们拼成可执行文件，还得解决”你这个文件用的 gdata1，在别的文件里定义”这类问题——靠的就是每个目标文件里的符号表。

链接时如果报 undefined reference to 'xxx' 或 LNK2019 这类错误，本质就是某个符号在别人的符号表里找不到。

所以，一个名字进不进符号表，取决于它需不需要被外部看见。而全局变量要被别的文件访问，自然得登记；出了函数就没人认得的局部变量，登记了也没用。

局部变量到底产生符号吗？

main 里的三个局部变量 a、b、c，在符号表中不会产生符号。

它们对应生成的是指令。在 x86 体系下，int a = 12; 生成的汇编是：

它没有产生 a 的符号，而是生成一条 mov 指令。这三个局部变量的定义，最终产生的是三条 mov 指令，指令放在 .text 段。

那”局部变量在栈上”这句话错了吗？

没错，但要分清两个层面，这是很多人的概念性错误：

  1. a = 12 这条语句编译后生成一条指令，这条指令放在 .text 段
  2. 当这条指令运行时，CPU 在当前进程的栈上开辟 4 字节空间，把 12 存进去

所以准确的表述是：**a 不是”在栈上”，而是”a = 12 这条语句生成的指令，运行时会在栈上开辟空间存放 12”。**

静态局部变量和局部变量不一样

静态局部变量也是放在数据段的，程序启动的时候不会初始化它们，而是第一次运行到它们的时候初始化。

所以 e = 13 放在 .data，而 f = 0、g 放在 .bss。
