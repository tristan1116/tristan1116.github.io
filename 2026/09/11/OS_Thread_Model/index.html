操作系统线程模型总览

进程是资源的容器，也是操作系统调度的基本单位。但现代操作系统里，真正被 CPU 调度的东西其实是线程。

线程的使用

在传统的操作系统设计中，进程是资源分配的基本单位，每个进程都拥有独立的地址空间和至少一个控制线程。

随着并发编程需求的增加，人们发现单一进程内运行多个控制流，能带来诸多优势。这些线程虽然彼此独立执行，但它们共享同一进程的地址空间及其中的所有数据，这种模式为多线程编程提供了基础。

资源共享

线程之间的主要优势在于它们能够共享同一块地址空间。线程可以直接访问进程中的全局变量、静态变量，以及通过指针或引用访问的内存区域，不需要进行进程间通信（IPC）那套复杂操作。

比如在一个文本编辑器里，多个线程可以同时访问并修改文档的同一部分，因为它们共享着文档的内存表示。

轻量级与高效性

相比进程，线程是更加轻量级的执行单元。线程的创建和销毁通常比进程快得多，因为线程不需要为每个实例分配独立的地址空间和其他系统资源。

在许多现代操作系统中，创建一个新线程的速度可以比创建一个新进程快 10 到 100 倍。这种高效性让线程成为处理高并发任务时的理想选择。

性能提升

在涉及大量计算和 I/O 处理的场景中，多线程编程能显著提升应用程序的性能。当 CPU 密集型任务与 I/O 密集型任务交替执行时，多线程允许这些任务重叠进行，从而减少 CPU 的空闲时间。

拿 Web 服务器举例：一个线程可以处理客户端的连接请求，另一个线程负责从磁盘读取数据并准备响应。这种并行处理方式提高了服务器的吞吐量和响应速度。

线程作为进程内的一种轻量级执行单元，通过共享地址空间和高效性，为并发编程提供了强大的支持。在现代软件开发中，多线程编程已经成为一种普遍采用的技术手段，用于提高应用程序的并发性和性能。

Web服务器：三种解决方案

在探讨线程应用的实例时，我们可以聚焦于web服务器的工作机制：

问题本身

客户端向服务器发送页面请求，服务器把页面返回去。值得注意的是，站点上各个页面的访问频率差得很远，公司主页这类页面被请求的次数远超产品详情页。

为了优化性能和响应速度，服务器采用了一种高效策略：把访问量高的那批页面预先加载进内存。这个用来存放高访问率页面的存储空间，就叫高速缓存（cache）。缓存命中就直接返回，不用访问磁盘。

注：CPU 里也是同样的思路，L1、L2、L3 缓存存的是近期可能被频繁访问的数据和指令，为的是减少对主存的直接访问。

多线程解决方案

Web 服务器的一种组织方式，核心是一个叫调度线程（dispatcher thread）的组件。

调度线程从网络接收工作请求，充当中央调度器。收到请求并完成初步检查后，它选择一个当前处于空闲（阻塞状态）的工作线程，把指向请求消息的指针写入该工作线程关联的数据结构（如队列或特殊字）中，然后唤醒这个处于休眠状态的工作线程，把它的状态从阻塞态转变为就绪态。

被唤醒的工作线程启动后，先检查请求所需的页面是否已存在于共享高速缓存中。存在就迅速检索并返回，不需要进行磁盘 I/O。不存在则执行 read 从磁盘读取，由于磁盘 I/O 通常耗时较长，工作线程会进入阻塞状态，等待磁盘操作完成。在此期间，调度线程会选择其他就绪的工作线程执行，确保服务器能够持续处理新的请求。

单线程解决方案

没有多线程环境时，服务器的主循环连续不断地获取客户端请求并依次处理。问题出在处理每个请求的过程中：一旦涉及磁盘 I/O 这类耗时操作，服务器必须等待这些操作完成，期间无法响应新的请求。

PDF 把这种状态称为”空转”，它显著降低了服务器的处理效率，每秒能够处理的请求数量非常有限，由此凸显出多线程对于提升程序并行性和整体性能的重要性。

状态机解决方案

还有第三种方案，专门针对那些只提供非阻塞系统调用（比如非阻塞 read）的环境。

非阻塞 I/O 的行为是这样的：把文件描述符设置成非阻塞模式之后，如果 I/O 操作不能立即完成（比如从网络读数据但当前没有数据到达），系统调用会立刻返回一个错误码（EAGAIN 或 EWOULDBLOCK），而不是让调用线程进入休眠状态等待。

非阻塞系统调用在需要处理多个IO源，或希望提高程序响应速度的场景中非常有用。通过将文件描述符设置为非阻塞模式，并使用适当的错误处理逻辑，程序可以在IO操作无法立即完成时继续执行其他任务，而不是阻塞等待。这有助于提高程序的并发性和整体性能。

状态机方案的工作流程：

  1. 请求到达服务器，接收线程先看内存中的高速缓存能不能立刻满足该请求。能就立即响应，无需任何等待。
  2. 如果缓存里没有所需数据，就发起一个非阻塞的磁盘读取，然后把请求的状态（请求标识符、预期的数据位置等）记进服务器的内部状态表。
  3. 服务器进入一个事件循环，不断监听和响应两类事件：新请求到达、先前磁盘操作完成（通常通过信号中断通知）。每当有新请求到来时，服务器检查其状态，如果处于可立即处理的状态，则开始处理；若需要等待磁盘响应，则跳过处理，继续监听。
  4. 一旦收到磁盘操作完成的通知，服务器就从状态表里取出对应的请求状态，用拿到的数据完成响应准备的工作，最后发给客户端。

这套设计体现的是有限状态机（Finite-State Machine，FSM）的核心思想。每个请求被看成一个有着有限数量状态的系统，系统根据外部事件（新请求到达、磁盘操作完成）从一个状态转移到另一个状态，每次转移都伴随着状态的保存和恢复。

FSM 的应用不限于 Web 服务器，凡是需要处理并发和异步事件的场合都能用上。但是编程难度相对较高，状态转移和状态信息的保存恢复都要开发者显式管理。

三种方案放一起比：

模型 特性
单线程 无并行性，性能较差，阻塞系统调用
多线程 有并行性，阻塞系统调用
有限状态机 并行性，非阻塞系统调用、中断

多线程靠并行处理提升性能，但是增加了复杂度和线程安全问题；单线程简单但性能受限；状态机用非阻塞调用和中断机制换来高性能，但是编程难度高。

经典的线程模型

换个角度看进程：它是一种高效整合并管理相关资源的方式。进程承载着程序正文和数据，还装着已打开的文件句柄、派生的子进程、待触发的定时器、信号处理机制、用户账号信息这些形形色色的资源。把它们统一封装在进程内部，资源的组织和访问都简化了。

而进程内部真正的执行单元是线程（thread）。每个线程配着三样关键的执行状态组件：

  • 程序计数器，精确追踪即将执行的指令位置
  • 寄存器集合，暂存线程当前操作所依赖的变量值
  • 堆栈，记录方法调用与返回的路径

线程的运行依托于进程，但进程和线程在概念上是截然分开的实体，各承载不同的职责，可以独立处理。一句话概括：进程是资源的容器，线程是 CPU 直接调度的执行单位。

线程概念的引入给进程模型加了一个新维度。同一进程内部，多个线程能以较高程度的独立性并行运行，彼此互不干扰。这种架构看起来类似一台计算机上同时跑多个独立进程，区别在于线程间的资源共享紧密得多，它们共同访问同一地址空间及其他进程资源。不同进程之间虽然也共享物理内存、磁盘、外设，但访问和隔离机制要复杂得多。

线程继承进程的资源，同时保持较轻量的执行上下文，所以常被叫做轻量级进程（lightweight processes）。多线程（multithreading）这个词，指的就是单个进程内部多个线程并行执行、共享资源、协同工作的模式。

共享带来便利，也带来风险。每个线程都有能力访问进程地址空间内的任意内存地址。一个线程不仅能读写自己的局部变量和堆栈，理论上它还能访问并修改同一进程中其他线程的堆栈或全局变量。比如某个线程错误地写进了一个被其他线程当作控制流程用的变量，或者覆盖了某个线程栈上的关键返回值，都可能引发难以预料的行为，甚至让程序崩溃。

所以，线程间的资源共享虽然提高了执行效率和响应速度，但也要求开发者在设计多线程程序时采取额外的同步和协调机制，保证线程间的正确交互和数据一致性。手段包括互斥锁（mutexes）、信号量（semaphores）、条件变量（condition variables）这些同步原语，以及合理的线程调度策略，用来避免数据竞争（race conditions）和其他并发问题。

线程的状态

stateDiagram-v2
    [*] --> 就绪
    就绪 --> 运行: 获得 CPU 时间片
    运行 --> 就绪: 时间片用完
    运行 --> 阻塞: 等待 I/O 或事件
    阻塞 --> 就绪: 事件发生
    运行 --> 终止: 任务完成 / 出错
    终止 --> [*]

线程是操作系统调度的基本单位，它的生命周期同样可以划分成多个状态，跟进程的状态类似，但更侧重 CPU 的调度与执行。线程可以处于这几种状态：

运行中（Running）：线程获得 CPU 时间片，进入运行状态，执行任务。时间片结束后，线程可能需要把 CPU 让给其他线程。

阻塞（Blocked）：线程因为某些原因，比如等待外部事件或资源的就绪，而暂停执行。比如执行一个从键盘读取数据的系统调用，它会一直等到有数据可读。等待文件 I/O 完成、等待网络响应也是常见的阻塞原因。线程通常保持阻塞状态，直到等待的事件发生或资源可用，或者被其他线程通过信号、条件变量之类的机制唤醒。

就绪（Ready）：线程已做好执行准备，但 CPU 被其他线程占着，暂时轮不到它。处于就绪态的线程已经完成所有必要的准备工作，只等 CPU 时间片分配下来。

终止（Terminated）：线程完成任务，或者因为错误、异常、程序逻辑被终止。进程状态图里没有画出这一状态，但它是线程生命周期的重要阶段，标志着线程执行的结束。

线程之间的状态转换和进程之间的状态转换本质相似，遵循相同的规则和逻辑。一个正在运行的线程可能因为等待 I/O 进入阻塞态，I/O 完成后再次进入就绪态等 CPU 时间片；就绪态的线程拿到时间片就开始执行，进入运行态。每个线程都有自己的堆栈。

线程系统调用

进程在其生命周期中通常从一个初始的单线程启动，这个线程是进程的主执行流。之后通过调用特定的库函数（比如 thread_create）创建新线程来执行并发任务。

thread_create 调用时需要指定新线程的某些属性，包括一个用于标识新线程的名称。调用成功后返回一个唯一的线程标识符，后续对线程的引用和管理都用它。

线程完成任务后应调用退出函数（如 thread_exit）优雅地结束执行。线程一旦退出，状态转变为终止，此后不再参与系统调度，占用的资源被回收。

thread_join 是一种常用的同步机制，让一个线程（等待线程）暂停执行，直到另一个特定线程（被等待线程）退出。这套机制实现了线程间的依赖管理和资源回收。线程的创建和终止，在逻辑上和进程的创建与终止有诸多相似之处，都涉及资源的申请、使用和释放。

线程同步是指在多线程环境下，通过一定的机制来协调各个线程的执行顺序，以保证它们能够按照一定的规则来访问共享资源或执行特定的任务。同步的目的是确保数据的一致性和程序的正确性。

thread_yield 允许当前运行的线程主动放弃 CPU，把执行机会让给同一进程内的其他线程或系统内的其他进程。这在需要公平调度或避免饥饿时特别重要，因为与进程不同，线程通常不会因时钟中断而自动放弃 CPU（具体取决于操作系统和调度策略）。通过 thread_yield，开发者可以更精细地控制线程的执行顺序和优先级。

POSIX 线程

为了让跨平台编写线程程序成为可能，IEEE 在标准 IEEE 1003.1c（通常叫 POSIX.1c，或简称 POSIX 线程标准）里详细定义了线程标准，引入了 Pthreads（POSIX 线程）库作为实现线程功能的一套标准接口。这一标准在多数 UNIX 系统及兼容系统中得到广泛支持。

Pthreads 不依赖于特定编程语言，是一个执行和并行计算模型。它允许开发者在单个程序中创建并控制多个时间上重叠执行的线程，每个线程代表一个独立的工作流程。它的实现在 FreeBSD、NetBSD、OpenBSD、Linux、macOS、Android、Solaris 上都存在。

Windows 本身不直接支持 POSIX 线程，但微软通过兼容层技术（如 Windows Services for UNIX，或后续版本的兼容性更新），在 Windows API 之上实现了对 pthread 功能的支持，使得 pthreads 程序也能在 Windows 平台上运行。

常用的几个调用：

线程调用 描述
pthread_create 创建一个新线程
pthread_exit 结束调用的线程
pthread_join 等待一个特定的线程退出
pthread_yield 释放 CPU 来运行另外一个线程
pthread_attr_init 创建并初始化一个线程的属性结构
pthread_attr_destroy 删除一个线程的属性结构

所有 Pthreads 都有一套特定属性，定义每个线程的基本特征。每个线程包含一个唯一的标识符、一组寄存器（含程序计数器）以及存储在特定结构中的其他属性集，包括堆栈大小、调度优先级和策略等。

  • pthread_create 成功执行后把新线程的标识符返回给调用者。这个机制和 UNIX 的 fork 系统调用相似，线程标识符在这里起到类似进程 ID（PID）的作用。
  • pthread_exit 终止自身，同时释放线程堆栈等分配的资源。
  • pthread_join 等待另一个特定线程的终止，调用时需指定被等待线程的标识符，直到该线程退出，调用线程才继续执行。
  • pthread_yield 请求系统把当前线程置于可运行状态中的较低优先级，让其他线程有机会运行。
  • pthread_attr_init 初始化一个线程属性对象并设为默认值，之后可以修改它来定制线程行为（如设置优先级）。不再需要时用 pthread_attr_destroy 删除并释放内存。这个过程只影响属性对象本身，对调用它的线程或任何已存在的线程没有影响。

线程的实现

主要有三种实现方式，划分依据是线程的创建、调度、管理这些工作交给谁做：

  • 在用户空间中实现线程
  • 在内核空间中实现线程
  • 在用户和内核空间中混合实现

在用户空间中实现线程

用户空间实现的意思是，线程的创建、调度、管理以及同步等机制完全由用户级库负责，不需要内核介入。线程对内核是透明的，内核根本不知道线程的存在，它只能看到进程。所以所有线程共享同一个进程空间，包括地址空间、文件描述符等。

上图中能直接看出用户空间实现的两个特征。线程表在用户空间的运行时系统内部，每个进程各有一张，记录本进程内各线程的程序计数器、堆栈指针、寄存器值以及当前状态。内核空间里只有进程表，没有线程表，内核能看到的只有进程，对线程一无所知。所以这张图里内核那一层不需要和线程层发生任何关系。

这种实现遵循一个通用架构：线程在运行时系统（Runtime System，也叫运行时环境）的监管下运行。运行时系统是程序执行的基础框架，提供程序运行的物理环境，还负责内存布局管理、变量访问机制、过程间参数传递、与操作系统底层的接口协调这些复杂任务。编译器设计时会根据目标运行时系统的特性做假设，保证生成的代码能正确执行。

运行时系统通常负责初始化和管理线程的堆栈，也可能包含垃圾收集、线程调度、语言内置的动态功能等高级特性。用户空间管理线程的场景下，每个进程都要维护一个专属的线程表（Thread Table）。这张表的作用类似内核中的进程表，但记录的是进程内部各线程的详细属性，包括程序计数器、堆栈指针、寄存器值以及当前状态。

线程发生状态转换时（比如从运行态转为就绪态或阻塞态），所有必要的恢复信息（执行上下文）都会存进线程表的对应条目。线程再次被调度时，运行时系统依据这些信息准确恢复线程的上下文，让线程从之前的状态无缝继续。这个过程跟内核在进程表里管理进程上下文在逻辑上是相似的，只是作用域和细节有区别。

举例来说，基于用户空间线程的 Java 应用程序里，JVM 的线程管理模块就扮演运行时系统的角色，负责创建、调度和管理 Java 线程，通过内部的线程表跟踪每个 Java 线程的状态和上下文信息。Java 线程因等待 I/O 阻塞时，JVM 把该线程的信息存进线程表，等 I/O 完成再在合适的时机恢复它。

优势

用户空间线程的线程状态信息保存在运行时环境提供的线程表里，调度程序（用户空间中的一个本地过程）从线程表里挑另一个就绪线程执行。整个过程完全在用户空间完成，避免了内核调用的开销，省去上下文切换，也不需要刷新 CPU 缓存。这种切换机制让用户空间线程在调度和执行上更快更灵活。

另外，调度算法可以定制。每个进程能根据自身需求定制调度算法，对需要精细控制线程执行顺序或优先级的应用尤其重要。比如带垃圾收集器的应用，用户线程可以确保垃圾收集线程在合适的时机运行，不会因内核调度的不确定性打断关键操作。

此外，用户空间线程能展现出良好的可扩展性。内核线程要占用内核的表空间和堆栈空间等资源，系统中内核线程数量过多时可能引发资源紧张甚至系统崩溃。用户空间线程由进程自身管理，不直接占用内核资源，大量线程存在时也能保持较好的稳定性和可扩展性。

劣势

阻塞系统调用：以键盘输入为例，一个线程发起系统调用等待键盘输入，在常规用户空间线程模型里，由于内核不直接知晓线程的存在，内核只能直接操控进程，所以会导致整个进程，包括进程内所有线程，被阻塞。这违背了线程设计的初衷之一，也就是允许线程进行阻塞调用而不影响同进程内的其他线程。用户空间线程库为了解决这个问题，通常要实现复杂机制，比如使用非阻塞 I/O、轮询，或者用专门的线程处理阻塞操作。

缺页中断：由于计算机内存有限，操作系统用分页机制管理内存。当程序访问到尚未加载到内存的页面时，会触发缺页中断，操作系统需要从磁盘加载缺失的页面。传统用户空间线程模型里，因为内核对线程无知，一个线程的缺页中断可能导致整个进程被阻塞，即使进程内其他线程处于可运行状态也执行不了。

调度上也有限制：在一个单进程内部，如果没有外部触发（比如时钟中断或线程主动让出 CPU），就无法实现基于时间的轮转调度。这意味着一旦某个线程开始执行，它会独占 CPU 直到自愿放弃，除非因为系统调用、等待 I/O 之类的原因为被阻塞，否则同进程内的其他线程拿不到执行机会。

为了解决上述问题，现代操作系统和线程库通常采用混合模式（详见最后的混合实现），结合用户空间线程和内核空间线程的优点。比如Java虚拟机JVM中的线程模型就是这么做的，Java 线程在用户空间被管理，但通过与内核线程的映射来处理阻塞调用和缺页中断，既保持用户空间线程的高效性，又解决了阻塞和调度上的难题。

在内核中实现线程

转向内核实现线程的方案后，系统架构发生显著变化：运行时环境不再是必需的，因为线程的管理和调度工作直接由操作系统内核承担。相应地，每个进程内部不再维护自己的线程表，所有线程的详细信息都被统一记录在内核维护的一个全局线程表里。

和用户空间实现的示意图对比，主要有两点区别：线程表只在内核空间里，全系统共用一张（全局线程表），各进程内部不再有自己的线程表和运行时系统。用户空间的线程要通过系统调用进入内核的线程表，这是图中那几条跨层连线的含义，也意味着每次线程操作都要陷入内核。

全局线程表是内核数据结构的一部分，跟踪系统中所有活动线程的状态、属性以及相互关系。当进程中的线程要创建或销毁线程时，它会发起一个系统调用请求，请求传递给内核处理，内核根据请求的类型（创建/销毁），在全局线程表里做相应更新。

例如，当线程执行 pthread_create 创建新线程时，内核接收到调用，在全局线程表中分配一个新条目，存储新线程的标识符、状态、优先级、堆栈信息等关键数据，同时为新线程分配内存和处理器时间等必要资源。

与之相对的，当线程通过 pthread_exit 或其他机制请求销毁自身时，内核更新全局线程表，把该线程状态标记为已终止并回收其占用的资源。如果这是进程中的最后一个线程，内核还可能回收进程占用的所有资源，结束进程。

这种方式提供了高度的系统可见性和控制能力，所有线程的创建、销毁和管理都由内核直接负责。但是性能开销相对较大，系统调用和内核级别的线程管理操作通常比用户空间内的操作更复杂、更耗时。

内核维护的线程表详尽记录每个线程的寄存器状态、执行状态及其他关键信息。内容和用户空间线程表一致，只是物理存储位置在内核空间，保证安全隔离和高效管理。此外内核还构建了一张进程表，全面跟踪整个系统的运行状态。

关于线程的阻塞与调度，所有可能引发阻塞的操作都通过系统调用机制实现。某个线程因等待资源或事件进入阻塞态时，内核有决策权，决定是否切换到同一进程内另一个就绪线程，或者调度一个来自不同进程的线程以充分利用系统资源。而在用户空间的运行时系统实现里，通常会坚持运行当前线程直到它的 CPU 时间片耗尽，或者没有其他可运行的线程可选时，内核才介入调度。

考虑到内核层面创建或销毁线程的开销较高，部分系统会采用线程复用策略优化性能。一个线程被销毁时，内核不立即释放其全部资源，而是把它标记为不可运行状态，保持内部结构的完整性。之后系统需要创建新线程时，优先复用这些已存在的线程资源，重新配置状态为可用，避免从零开始构建线程的开销。

当进程中的某个线程遭遇缺页故障时，内核能迅速检测并评估系统内其他可运行线程的情况。必要的时候，也就是等待所需页面从磁盘加载进内存的过程中，内核会选一个可运行的线程继续执行，保持系统的响应性和效率。但是这种灵活调度也伴随着成本，即系统调用的相对高昂代价。在频繁进行线程操作（如创建、终止）的场景中，可能会因系统调用的累积效应而显著增加总体开销。

混合实现

为了融合用户空间与内核空间的优点，设计者引入了一种名为内核级线程（也叫内核线程）的机制，并把用户级线程与这些内核线程中的部分或全部进行高效的多路复用。这一设计赋予开发者极大的灵活性，可以根据具体应用场景控制用户线程与内核线程的数量比例。

在这个模型里，每个内核级线程都是操作系统直接管理的独立调度实体。操作系统内核只负责识别、创建、调度以及管理这些内核级线程。与此同时，多个用户级线程可以绑定到同一个内核级线程上，实现资源的共享与复用。多路复用机制提高了系统资源的利用率，在并发执行大量轻量级任务时，能显著减少线程创建与销毁带来的开销。

举例来说，假设一个应用程序需要处理大量I/O密集型任务，它可能会创建多个用户级线程来并发执行这些任务。然而，由于IO操作通常会导致线程阻塞，如果直接位每个用户线程分配一个内核线程，将会造成大量内核线程的闲置等待。通过采用内核级线程与用户级线程的多路复用，这些用户线程可以共享少数几个内核线程，当某个用户线程因为IO操作而阻塞时，内核线程可以无缝切换到另一个就绪的用户线程执行，从而避免了资源浪费，提高了整体的并发处理能力。
