STM32——串口中断模式通信，让CPU不再"傻等"

发表于 2026-07-29 分类于 嵌入式 阅读次数：
本文字数： 9.5k 阅读时长 ≈ 9 分钟
上一篇博客用轮询模式实现了串口通信——电脑发指令，STM32控制LED。但轮询模式有个大问题：CPU一直在while循环里"傻等"，除了接收信息，啥也干不了。这篇用中断模式解决它：开启串口中断后，CPU该干嘛干嘛，数据到了自动触发中断处理，不再干等。

从轮询到中断

上篇博客，我们用串口的轮询模式实现了电脑控制 LED。当时的代码长这样：

这里存在一个问题：在 HAL_UART_Receive 等数据的时候，CPU 在干什么？

答案是——在空转查询，一直在问”数据到了吗？到了吗？到了吗？”

这就好比你等外卖：

  • 轮询模式：每5秒跑去门口看一眼，啥也干不了，饭来了才回去吃
  • 中断模式：装个门铃，该干嘛干嘛，门铃响了再去拿

显然，中断模式高效得多。这篇就来把上一版的轮询代码改成中断模式。

中断模式：让”门铃”代替”傻等”

中断模式的思路完全不同：

区别在哪？CPU 不再主动查询，而是由硬件在数据就绪时通知 CPU。 这个”通知”就是中断。

具体来说，中断模式下，每发送完一个字节或每接收到一个字节，串口硬件都会触发一次中断，把 CPU “叫回来”处理下一个字节。HAL 库在中断处理函数里把这些事都做好了，我们只需要：

  1. 在 CubeMX 中开启串口中断
  2. 把 HAL_UART_Receive 换成 HAL_UART_Receive_IT
  3. 把 HAL_UART_Transmit 换成 HAL_UART_Transmit_IT
  4. 把处理数据的逻辑写到回调函数 HAL_UART_RxCpltCallback 里

改动一：接收数组变成全局变量

原来的 receiveData 定义在 main() 内部（局部变量），现在要提到外面变成全局变量，因为回调函数里也要用它。

为什么？ 局部变量只在 main() 函数内有效，而回调函数 HAL_UART_RxCpltCallback 在 main() 外部，访问不到 main() 里的局部变量。提升为全局变量后，整个文件都能访问它。

改动四：核心逻辑移到回调函数

真正的变化在这里——所有串口数据的处理逻辑，从 while 循环搬到了回调函数中：

第4步非常关键——为什么要在回调函数末尾再次调用 HAL_UART_Receive_IT？

中断接收是”一锤子买卖”：调用一次 HAL_UART_Receive_IT，它接收完指定长度的数据后，就会停下来。如果不再次调用，下一次串口发数据来，就没人在乎了。

这就好比你按了一次门铃——门铃是一次性的。如果下次来人，找不到门铃可以通知你，你就不知道。

所以在回调函数的最后，必须**重新”装好门铃”**：调用 HAL_UART_Receive_IT 启动下一次中断接收。

函数对比总结

功能 轮询模式 中断模式
发送 HAL_UART_Transmit(&huart2, buf, len, timeout) HAL_UART_Transmit_IT(&huart2, buf, len)
接收 HAL_UART_Receive(&huart2, buf, len, timeout) HAL_UART_Receive_IT(&huart2, buf, len)
超时参数 ✅ 有 ❌ 不需要
CPU 占用 一直占用，直到完成 仅中断时短暂占用
数据在哪处理 while 循环中 回调函数中

补充：什么是回调函数？

“回调函数”这个名字听起来挺唬人，但本质上就是个普通的函数。它特殊的地方在于——不是你在代码里主动调用的，而是 HAL 库在特定事件发生时自动帮你调用的。

你把函数地址告诉 HAL 库 你定义了 HAL_UART_RxCpltCallback 这个函数（相当于留了电话号码）

和轮询模式的对比

轮询模式是你主动去问，中断模式是你留下联系方式等着被通知。回调函数就是那个”联系方式”。

解读新增的初始化代码 —— NVIC 与中断向量

CubeMX 开启 USART2 中断后，生成了三段和中断相关的代码。

1. stm32f1xx_it.c —— 中断服务函数

这个函数是中断向量表中 USART2 对应的中断服务函数。当串口触发中断时，CPU 暂停当前任务，跳到这里执行。

函数体只有一行：调用了 HAL_UART_IRQHandler(&huart2)。这是 HAL 库提供的中断分发函数，它的内部做了判断逻辑，然后把不同的情况分发给对应的回调函数。

关键问题是：它怎么知道我收到几个字节了？又是什么时候调用的回调函数？

要回答这个问题，得翻开 HAL 库源码看看。在vscode中，把鼠标停在 HAL_UART_IRQHandler 上按右键，找到定义栏，点进去，就能看到它的实现（下面放了简化版）：

条件 含义 谁设置的
USART_SR_RXNE 状态寄存器中的”接收数据寄存器非空”标志——串口硬件收到一个字节后自动置1 ✅ 硬件自动

2. stm32f1xx_hal_msp.c —— NVIC 配置

CubeMX 在 HAL_UART_MspInit 中添加了两行新代码：

这两行的作用：

函数 作用
HAL_NVIC_SetPriority(中断号, 抢占优先级, 子优先级) 设置这个中断的优先级。数字越小优先级越高。0, 0 就是最高优先级
HAL_NVIC_EnableIRQ(中断号) 使能中断——告诉 NVIC，这个外设的中断请求可以被响应了

如果不调用 HAL_NVIC_EnableIRQ，即使外设触发了中断，NVIC 也不会把它发给 CPU——中断就被”屏蔽”了。

3. 回调函数的 __weak 弱定义

如果你在 HAL 库源码里搜索 HAL_UART_RxCpltCallback，会看到这样的定义：

__weak 是弱定义——它像一个”占位符”。编译器看到弱定义后，如果在其他地方找到了同名但非弱定义的函数，就会用那个新函数覆盖掉弱定义。

所以，只需要在 main.c 中定义一个同名的 HAL_UART_RxCpltCallback，编译器就会自动使用我们的版本，HAL 库的中断分发逻辑就会在接收到数据时调用我们的函数。

如果你不在 main.c 里定义这个函数，HAL 库的弱定义版本就会被使用——它啥也不干，所以数据收到了也没反应。

轮询模式与中断模式对比

对比维度 轮询模式 中断模式
CPU 利用率 ❌ 低——一直在查询，浪费 CPU ✅ 高——只在数据到达时短暂处理
代码位置 while 循环中，顺序执行 回调函数中，事件驱动
多任务能力 ❌ 差——被串口阻塞时啥也干不了 ✅ 好——while 里可以做其他事
代码复杂度 ✅ 简单直观 ❌ 稍复杂（需理解中断和回调）
适用场景 简单 demo、只有串口任务的项目 多任务、需要高效利用 CPU 的项目

总结

这篇博客的核心变化是：

把代码从 while 循环搬到回调函数，把 HAL_UART_Receive 换成 HAL_UART_Receive_IT。

学了这篇，STM32 就具备了”事件驱动”的能力——外设不再需要 CPU 不停地轮询，而是在需要的时候主动通知 CPU。这是从简单裸机编程走向复杂嵌入式开发的必经之路。
