STM32——OLED屏幕：CH1116驱动原理与波特律动驱动库

发表于 2026-08-03 分类于 嵌入式 阅读次数：

本篇博客学习128×64 的 OLED 屏幕：先搞懂驱动芯片 CH1116 的页/列/显存原理，从点亮一个像素开始手写底层；再用上波特律动的OLED 驱动库 + LED 取模助手，画线画圆、显示图片、显示中文。

本篇主要学习：驱动一块 128×64 的 OLED 屏幕。它同样挂在 I2C1 总线上，所以我们之前学的 I2C 收发全部复用，本篇的核心增量是：

和上一篇的区别 上一篇（AHT20） 本篇（OLED）
数据方向 读传感器数据（Receive） 写屏幕数据（Transmit）
数据量 几字节 每帧 1KB（128×64 位）
编程模式 轮询→中断→DMA 状态机 显存（双缓冲思想）
关键知识 状态机、static、extern 页/列寻址、取模、驱动库

硬件原理：屏幕是怎么亮起来的

像素与分辨率

所谓屏幕，其实就是一个个发光小灯组成的阵列，每个小灯叫一个像素。屏幕上小灯的排列数目就是分辨率。这块 OLED 是 128×64——128 列 × 64 行，一共 8192 个像素。

如果像控制 RGB 灯那样一个 IO 控制一个像素，得 8000 多个引脚——显然不可能。所以屏幕都带一颗驱动芯片：我们只需要通过 I2C/SPI 和芯片通信，由它去操纵这 8000 多个小灯的亮灭。keysking学习板上用的是 CH1116，常见的还有 SSD1306，都能驱动 128×64 的 OLED，原理大同小异，只是部分指令和特殊功能有差异。

类比：驱动芯片就像”包工头”——你只要给包工头下达指令（哪个灯亮），不用自己去一个个拉线。

页（Page）结构——1 字节管 8 个像素

CH1116 把屏幕划分为 8 个页（Page），每页 128 列 × 8 行：

为什么要分页？因为一个字节正好 8 位——一字节数据就能表示某一页某一列 8 个像素的亮灭。比如告诉芯片”第 0 页第 3 列设为 0xC1（1100 0001）”，那么这一列从上到下第 0、1、7 位对应的像素亮起，其余熄灭。

I2C 通信格式：指令 0x00 开头，数据 0x40 开头

CH1116 的 I2C 地址是 0x7A。跟它通信分两类：

  1. 指令：I2C 地址 + 0x00 + 指令字节。比如：
    • 设置页地址：0xB0 ~ 0xB7（第 0 页是 0xB0，第 7 页是 0xB7）
    • 设置列地址：分两次发送——先发低 4 位（如 0x0A 表示低 4 位是 A），再发高 4 位（如 0x15 表示高 4 位是 5），合起来列地址 = 0x5A
  2. 数据：I2C 地址 + 0x40 + 任意数量数据字节，芯片按当前的页/列地址把数据代表的像素亮灭显示出来。

记忆方法：0x00 是”命令门牌号”，0x40 是”数据门牌号”——告诉芯片接下来要进来的字节是干什么的。

列地址自动 +1——“偷懒”神器

CH1116 有个非常方便的特性：写完一字节的 8 个像素后，列地址自动加 1。这样我们只需要把页地址设为 0、列地址设为 0，然后一股脑发送 128 个字节，就完成了一整页的设置；页地址递增，循环 8 次，就点亮了整块屏幕。

CubeMX 配置

1. I2C 提速：标准模式 → 快速模式

I2C1 之前已经用过了，这集只需要做一个小改动：OLED 数据量大（每帧要发 1KB+），把 I2C 速度从标准模式（100K）改为快速模式（400K）。

2. 时钟：把系统时钟配到 72MHz

截止到本集，我们的 STM32 一直跑在内部时钟 HSI 8MHz 上。为了跑得更快，这集要切换到学习板上的外部晶振（HSE 8MHz）并倍频到 72MHz：

  1. System Core → RCC → 把 High Speed Clock (HSE) 设为 Crystal/Ceramic Resonator（外部晶振）
  2. Clock Configuration → 把 HCLK 输入框改为 72
  3. CubeMX 自动配置时钟树：HSE 8MHz × PLL 倍频 9 = 72MHz

注意：要先开 HSE 再改 HCLK。若顺序颠倒，CubeMX 只能用内部时钟 HSI（PLL 输入 4MHz、最大倍频 16 倍，极限 64MHz）配不出 72MHz，会弹出 “no solution found using 72MHz” 提示改用 64MHz。

老规矩：Project Manager → Code Generator → 勾选 **”Generate peripheral initialization as a pair of ‘.c/.h’ files per peripheral”**，每个外设单独生成 .c/.h 文件。

5. 中文是怎么显示出来的（取模助手干了什么）

波特律动取模助手生成的中文字模，每个字模的前 4 个字节存的是这个字的 UTF-8 编码：

驱动库的 OLED_PrintString 遍历字符串，用 _OLED_GetUTF8Len 识别每个中文字符的 UTF-8 编码长度（3 字节），在字库里逐条比对前 4 字节找到对应字模，再 OLED_SetBlock 画到显存。这就是为什么可以直接写中文字符串而不需要查表——前提是：

  1. 编译器字符集设置为 UTF-8
  2. 字模用波特律动取模助手生成（带 UTF-8 前缀的格式）

传统 PCtoLCD2002 之类软件没有这个设计，显示中文得一个一个字查坐标，这也是 keysking 写这个取模助手的初衷。

解读初始化代码

1. SystemClock_Config：72MHz 是怎么来的

HSE 8MHz 不分频进 PLL，倍频 9 倍 → 72MHz。FLASH_LATENCY_2 是跑 72MHz 时必须的 Flash 等待周期（CPU 比 Flash 快，需要插入等待）。

2. MX_I2C1_Init：快速模式

I2C 时钟在 APB1 总线上（36MHz），400kHz 快速模式的占空比由 I2C_DUTYCYCLE_2 决定。

3. HAL_I2C_MspInit：引脚复用

复用开漏是 I2C 引脚的关键：I2C 协议靠”释放总线 = 高电平”工作，开漏输出 + 外部上拉电阻实现线与逻辑。

踩坑记录

🕳️ 坑 1：OLED 上电比 STM32 慢

STM32 启动（毫秒级）比 OLED 上电快，初始化太早 OLED 没准备好会白屏。所以 OLED_Init() 前加 HAL_Delay(20)。

🕳️ 坑 2：刚上电”花屏”

CH1116 显存里的数据是随机的——数据为 1 的地方像素亮、为 0 的地方熄灭，所以刚点亮时屏幕是杂乱的花屏。OLED_NewFrame()（清显存）+ OLED_ShowFrame() 刷一帧全 0 就干净了。

🕳️ 坑 3：列地址偏移 2 位

学习板上的屏幕为了滚屏等操作，列地址整体左移了 2 位：想点亮”第 0 列”，实际要设置列地址 0x02。所以 OLED_ShowFrame 里列地址低 4 位写的是 0x02 而不是 0x00，第一次手写驱动的人很容易栽在这。

总结

新知识点

知识点 一句话
驱动芯片 CH1116 通过 I2C 指令操纵 8192 个像素的”包工头”
页结构 8 页 × 128 列 × 8 行，1 字节 = 一列 8 像素
指令/数据格式 0x00 开头是指令，0x40 开头是数据
列地址自动 +1 设好页/列后连续发 128 字节 = 刷完一页
显存（双缓冲） 先画草稿纸，再一次性刷屏
Bresenham 算法 只用整数运算的画线算法
取模助手 波特律动 LED 取模助手生成字模/图模，带 UTF-8 前缀
时钟树 HSE 8MHz × PLL9 = 72MHz，HSI 极限 64MHz

与上一篇的对比

上篇的 AHT20 是”读”数据（Receive + 状态机），本篇的 OLED 是”写”数据（Transmit + 显存）；上篇解决”数据怎么来”，本篇解决”数据怎么展示”。两者共用 I2C1 总线——I2C 是一个多从机总线，设备地址不冲突就可以挂在同一条线上，这也是将来温湿度上屏（AHT20 读到 → OLED 显示）的伏笔。
